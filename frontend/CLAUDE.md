# Mobile App (React Native) — Rules

Parent rules: `../CLAUDE.md`. Read them first. This file covers the member mobile app for iOS and Android.

## 1. Scope

Screens that map to the PRD modules:

| Module | Screens |
|---|---|
| 1. Onboarding | Register, log in, profile setup (name, contact, address, birthday), choose membership tier, "awaiting activation" state |
| 2. Membership card | Digital card: member name, member ID (`BC-…`), expiry date, active/inactive badge, verification code |
| 3. Partner directory | Category filter (Fuel, Groceries, Dining, Car Rentals, Services, …), partner list, partner profile (logo, address, contact, offer terms, redemption method) |
| 4. Voucher claim | Offer detail with "Claim Voucher Code" button, voucher screen showing the single-use code, voucher status list |
| 5. Notifications | Push permission prompt, notification handling, deep link to the voucher or card |

Nothing else. No web views of partner sites, no in-app payments, no social features.

## 2. Structure

```
frontend/
  src/
    app/           # navigation and screen routing
    features/
      auth/
      onboarding/
      membership/  # card, verification code
      partners/
      vouchers/
      notifications/
    shared/
      api/         # typed API client generated from Swagger
      components/
      theme/
      hooks/
      utils/
    config/        # environment (API base URL) — no secrets
  __tests__/
```

Each feature owns its screens, hooks, and components. Shared code goes in `shared/` only when a second feature needs it.

## 3. API client

- Generate the typed client from the backend's Swagger/OpenAPI spec. Do not hand-write request types that the spec already defines.
- All calls go through one client that adds the auth header, handles token refresh once, and maps error codes to user-facing messages.
- Show the user a clear message for every documented error code. Never show raw server text.

## 4. Authentication and storage

- Store the access and refresh tokens in the platform secure store (Keychain on iOS, Keystore on Android). Never in AsyncStorage or plain files.
- Clear all tokens and cached member data on logout.
- If a refresh fails, send the user to log in. Do not loop.
- Never store full voucher codes, card numbers, or personal details in logs, crash reports, or analytics events.

## 5. Membership card and verification code (Module 2)

- The card shows member name, `BC-` member ID, expiry date, and an Active or Inactive badge. The badge must match the server's status, not a local guess.
- Inactive members see the card in a clearly disabled state and cannot claim vouchers.
- The verification code is generated by the server. The app displays it and may refresh it on request. Never generate codes on the device.
- Show the code large enough for a cashier to read, with a copy action.
- Keep the card usable offline for the last known state, with a visible "last updated" time.

## 6. Partners and offers (Module 3)

- Cache the partner list for a short period. Refresh on pull-to-refresh.
- Category filter is applied to the cached list, then to the server if the list is paginated.
- Partner logos load through a placeholder; a missing logo never breaks the layout.
- Redemption method (code or voucher) is shown on every offer. Do not show a redeem action that the partner does not support.

## 7. Voucher claim (Module 4)

- "Claim Voucher Code" is disabled while the request is in flight, to prevent double taps. The server still enforces single claim.
- On success, show the single-use code once, with clear instructions: show it at checkout or enter it on the partner site.
- After redemption or expiry, the code is shown as used or expired and cannot be copied as active.
- Voucher statuses shown to the user: Claimed, Redeemed, Expired. Use the server's status values exactly.

## 8. Push notifications (Module 5)

- Ask for notification permission at a sensible moment (after first login, with a reason), not on first launch.
- Register the FCM token with the backend after login and update it when it changes. Remove it on logout.
- Tapping a notification opens the relevant voucher or card screen. Verify the member is still signed in before navigating.
- Notification text contains no personal data and no full voucher code.

## 9. UI and accessibility

- Minimum tap target 44×44 pt. Support dynamic text size.
- Color is never the only signal: pair "Active" and "Inactive" with a label and icon.
- Support both iOS and Android conventions for back navigation and safe areas.
- Dark mode support comes from the theme, not per-screen colors.
- Loading, empty, and error states are required on every screen that fetches data.

## 10. Money and dates

- Show prices from the server (plan price, offer value) in the member's currency. Do not calculate membership totals on the device.
- Format dates in the device locale. Store and send dates in UTC.
- The birthday field is a date only, with no time zone shift.

## 11. Conventions

- TypeScript strict mode. No `any` without a comment explaining why.
- Components are function components with typed props.
- No `console.log` in committed code. Use the shared logger, which strips personal data.
- Keep screens thin: business logic goes in hooks or the API layer.
- One feature per pull request where possible.

## 12. Testing

- Unit tests for hooks and utilities (date formatting, category filter, status mapping).
- Component tests for the card (active and inactive), the claim button (disabled while loading), and error messages.
- Test the claim flow end to end on both iOS and Android before each release build.
- Snapshot tests only for stable components, not whole screens.

## 13. Build and release

- Use Expo EAS (or the chosen CLI) for builds. Keep build profiles for development, preview, and production.
- Environment selection by build profile, not by editing code. No production API URL in development builds.
- Do not submit to the Apple App Store or Google Play without explicit approval. The PRD budgets $25 (Google) and $99/year (Apple) for publishing.

2. Navigation library (React Navigation is the default assumption).
3. How a member's partner-side redemption is confirmed in the app, if at all.
