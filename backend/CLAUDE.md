# Backend API — Rules

Parent rules: `../CLAUDE.md`. Read them first. This file covers the Node.js REST API only.

## 1. Scope

The API serves:

- Member registration, login, profile, and membership state
- Partner directory and offers (read)
- Verification code generation and voucher claim, use, and status
- Admin activation endpoint (separate role)
- FCM token registration and push triggers
- Swagger UI at `/api-docs`

It does not render web pages, process card payments, or store payment card data.

## 2. Structure (propose, then confirm; §9 lists the open framework choice)

Organize by module, not by technical layer:

```
backend/
  api/               # Vercel serverless function entrypoint (index.ts)
  src/
    modules/
      auth/          # register, login, refresh, logout
      members/       # profile, membership state, member ID
      membership/    # plans, tiers, activation (admin)
      partners/      # directory, categories, partner profile
      offers/        # offers per partner
      vouchers/      # claim, verify, redeem, status lifecycle
      notifications/ # FCM token registry, push triggers
      admin/         # admin-only endpoints
    shared/
      db/            # postgres (neon/supabase) + mongo (atlas) clients, migrations
      auth/          # jwt verify, role guards
      errors/        # error classes and mapper
      logger/
      validation/
    config/          # typed env config, one place
    docs/            # swagger setup
  test/
  migrations/
  vercel.json        # routing, headers, and cron jobs
```

Each module owns its routes, service, repository, schemas, and tests. Modules call each other through their service, never through another module's database tables directly.

## 3. Endpoints

- Version the path: `/api/v1/...`.
- Use plural nouns: `/members`, `/partners`, `/vouchers`.
- Use HTTP verbs correctly. Claiming a voucher is `POST /vouchers`. Redeeming is `POST /vouchers/{id}/redeem`. Activating a member is `POST /admin/members/{id}/activate`.
- Status codes:
  - `200` read or update, `201` created, `204` no body
  - `400` invalid input, `401` not signed in, `403` signed in but not allowed (for example, inactive member), `404` not found, `409` conflict (voucher already redeemed, duplicate email), `422` business rule failed, `429` rate limited, `500` never on purpose
- Error body is always the same shape: `{ "error": { "code": "VOUCHER_ALREADY_REDEEMED", "message": "...", "requestId": "..." } }`. Codes are stable strings, documented in Swagger.
- Every response carries a `requestId` header for tracing.

## 4. Swagger (Module 6)

- Served at `/api-docs`. Generated from the code, not hand-written.
- Every endpoint documents: summary, auth requirement, request schema, every response schema, every error code, and example values.
- Swagger must not be exposed without auth in production if it reveals admin routes. Decide with the team first (see parent §8).
- A PR that adds or changes an endpoint without a Swagger update fails review.

## 5. Authentication and sessions

- Email + password only. Reject any other sign-up method.
- Login returns a short-lived access JWT and a refresh token. The refresh token is stored hashed in the Postgres `sessions` table, keyed by session ID, and revoked on logout or password change.
- Every member request checks the JWT signature, expiry, and that the session still exists (and has not expired) in Postgres.
- If the session store is unreachable, authentication must fail closed (deny), never open.
- Admin role is a claim checked by a guard. Admin endpoints must not accept member tokens.
- Password reset and email verification (if added) need their own tokens with short expiry and single use. Ask before adding.

## 6. Membership and activation

- New members are created with status `inactive`.
- Only the admin activation endpoint changes status to `active`. Record who activated, when, and the payment reference, in Postgres. Write an audit event to Mongo.
- Activation must be idempotent: activating an active member returns `200` with the current state, not an error.
- Member ID (`BC-` + digits) is generated by the database sequence, not in application code, so it cannot collide.
- Expiry is computed from the plan and activation date. Store the expiry date; do not recompute it per request.

## 7. Vouchers (Module 4) — highest risk area

- A voucher code is generated with a cryptographically secure random generator. Never use `Math.random`.
- Codes are unique (database unique constraint), not just checked in code.
- Claiming:
  - Member must be `active` and not over their claim limit (limit from config).
  - Offer must be live (within its date window and not paused).
  - Runs in one transaction. Check and insert together.
  - Returns the code once. Store only a hash of the code if the design allows; decide with the team (parent §8).
- Redeeming:
  - Conditional update: `UPDATE vouchers SET status='redeemed' WHERE id=? AND status='claimed'`. If zero rows changed, return `409 VOUCHER_ALREADY_REDEEMED`.
  - Record the redemption (partner, time, amount if given) in Postgres and an event in Mongo.
  - A redemption is never reversed silently. Corrections are a separate, audited admin action.
- Expiry: a scheduled job moves `claimed` vouchers past their expiry to `expired`. On Vercel, this is triggered via Vercel Cron Jobs (`vercel.json`) calling a secured endpoint (`/api/v1/cron/expire-vouchers`) protected with a `CRON_SECRET` header. The job must be safe to run twice.
- A redemption always checks Postgres. Never redeem based on a cached value.

## 8. Push notifications (Module 5)

- Use FCM only. Store device tokens per member and device; remove tokens FCM reports as invalid.
- Triggers: voucher claimed, voucher redeemed, membership near expiry.
- Send pushes from a queue or after the database commit, never inside the transaction. A failed push must not roll back a voucher.
- Push payloads contain no personal data and no full voucher code.

## 9. Open decision

- Framework: Express or NestJS. Configured for Vercel Serverless Functions (e.g. `@vendia/serverless-express` for Express or NestJS serverless handler). Do not start scaffolding until this is decided. If not decided, ask.

## 10. Databases

- Postgres (Neon / Supabase): migrations only. Never change schema by hand. Each migration is reversible or marked irreversible in its header. Must connect through a serverless connection pooler to prevent exhausting connections during concurrent serverless invocations.
- Mongo (MongoDB Atlas): define a schema or validator for each collection. No unbounded documents; cap arrays. Cache client singleton outside handler to reuse connections across warm serverless executions.
- No Redis. Sessions and rate-limit counters are Postgres tables; expired rows are deleted by the daily `/api/v1/cron/purge-expired` job.
- Every query that reads user data filters by member or admin scope. Never trust an ID from the request alone.

## 11. Logging and audit

- Structured JSON logs with `requestId`, `memberId` (never email or name), route, status, and duration.
- Audit events (Mongo) for: registration, activation, voucher claim, voucher redeem, voucher expire, admin changes.
- Never log passwords, tokens, refresh tokens, FCM tokens, or full voucher codes.

## 12. Testing

- Unit tests for business rules in §4 and §7 (claim limits, atomic redemption, status transitions, idempotent activation).
- Integration tests against real Postgres and MongoDB (Docker), not mocks, for voucher claim and redeem.
- A concurrency test for redemption: two parallel redeem calls, exactly one succeeds.
- Every endpoint has a Swagger-matching contract test.

## 13. Commands (fill in once the framework is chosen)

- Install: `npm install`
- Dev: `npm run dev` or `vercel dev`
- Test: `npm test`
- Lint and typecheck: `npm run lint && npm run typecheck`
- Migrate: `npm run migrate:up`
- Deploy: `vercel` (preview) / `vercel --prod` (production)
